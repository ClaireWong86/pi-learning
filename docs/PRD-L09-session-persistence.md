# PRD L09：会话持久化与多轮追问

版本：v1.0（2026-10-28）
状态：已评审，直接执行
所属项目：pi-learning / L07-streaming 销售数据 Agent + L08-assistant-ui

## 1. 背景与问题

当前销售数据 Agent 的会话是“假多轮”：

- 服务端用 `SessionManager.inMemory()`，会话只活在进程内存里，服务重启即丢失。
- 服务端只有一个全局 session，前端靠“不传 fresh”隐式续聊；切换用户会把会话 dispose 掉重建。
- 前端每次只发送最后一条用户消息，线程状态与服务端的会话状态没有任何显式对齐手段，出问题无从排查。
- 评测全部是单轮题（`fresh: true` 逐题隔离），“那华南呢”“2 月呢”这类真实使用中最常见的省略式追问完全没有被测过——模型是否会用错上文口径（日期、筛选、对比方式）无人知道。

学习目标（L09）：掌握 Pi 的持久化 `SessionManager`（create / open 恢复 / buildSessionContext）、会话文件格式与按用户隔离的会话索引设计。

产品目标：用户关掉页面、服务重启之后，回到同一个话题能接着问；每次追问都沿用上文已确认的口径，而不是重新猜。

## 2. 目标与非目标

### 2.1 目标

1. 会话落盘：每个对话线程对应一个 Pi 会话文件，进程重启后可按线程恢复并续聊。
2. 显式线程协议：请求/响应都带 `threadId`，线程与用户绑定，杜绝跨用户串话。
3. 多轮追问可评测：新增一组多轮对话题目（含跨轮下钻），并给出单独通过率。
4. 前端可控：用户能开新对话、切换用户时不串线程；刷新页面后服务端上下文不丢（上下文在服务端，前端只需记住 threadId）。

### 2.2 非目标（本期不做）

- 多用户高并发调度与会话缓存淘汰（仍保留单线程忙碌保护，仅从“全局一把锁”细化到“同线程一把锁”）。
- 前端历史消息回显（打开旧线程时把过往对话渲染回线程列表）——列入下一迭代。
- 会话分支/回放（fork）、上下文压缩（compaction）——后续课时。
- 真实登录鉴权（京 ME 免登）——产品化迭代时接入，本期仍用演示用户。

## 3. 用户故事

- 作为财务（李先生），我问完“2026 年 1 月华东总销售额”，能直接追问“那华南呢？”，系统沿用 1 月口径只换地区，且数字正确。
- 作为财务，我中途关掉页面去开会，回来（哪怕服务重启过）继续问“其中笔记本卖了多少台？”，系统知道“其中”指刚才那批数据。

- 作为开发者，我跑评测时能单独看到“多轮对话通过率”，而不是和单轮题混在一起。

## 4. 功能需求

### FR1 会话存储层

- 新增会话存储模块，职责：
  - 线程创建：生成 `threadId`（UUID），用持久化 `SessionManager` 在会话目录建文件，记录索引。
  - 线程恢复：按 `threadId` 找到会话文件并 `SessionManager.open` 恢复，`buildSessionContext` 的消息数用于判定 `resumed`。
  - 线程索引：`index.json` 与会话文件同目录保存，条目含 `threadId / userId / sessionFile / createdAt / updatedAt / title / turns`。索引缺失或损坏时可由目录内会话文件重建（至少不崩溃）。
  - 用户绑定：线程创建后归属固定 `userId`；其他用户访问返回 403 语义的错误，不新建、不串用。
- 会话目录由环境变量 `SALES_SESSION_DIR` 覆盖，默认 `L07-streaming/data/sessions/`；评测/冒烟使用临时目录，不污染默认目录。

### FR2 聊天接口协议（向后兼容）

`POST /chat` 请求体扩展：

| 字段 | 规则 |
| --- | --- |
| `message` | 必填，同现状 |
| `userId` | 必填，同现状 |
| `threadId` | 可选，可由前端预先生成。首次出现的 id 即按此 id 建线程，再次出现则恢复；缺省时复用该用户最近一个线程，没有则新建（兼容旧前端） |
| `fresh` | 可选。`true` 时强制新建线程（评测逐题隔离依赖此语义），忽略传入的 `threadId` |

- `trace_start` / `trace_end` 事件回带 `threadId` 与 `resumed`（是否从已有会话恢复）。
- 同一线程同时只允许一个进行中的请求，冲突返回 429（信息注明是本线程忙）；不同线程互不阻塞。
- 评测现有的 `{message, userId, fresh: true}` 调用行为不变。

### FR3 线程查询接口

- `GET /api/threads?userId=`：返回该用户的线程列表（`threadId / title / turns / createdAt / updatedAt`），按更新时间倒序。
- `GET /api/threads/:threadId/history?userId=`：返回该线程的历史消息摘要（角色 + 文本），供排查与下一迭代的历史回显使用；线程不存在 404，跨用户 403。

### FR4 前端行为

- 前端持有当前 `threadId`（state + ref），每次请求携带；从 `trace_start` 同步服务端回带的 `threadId`。
- “开启新对话”按钮：生成新 `threadId` 并重置线程视图（以 key 变更重挂运行时实现）。
- 切换用户即开启新线程，避免把旧用户的 `threadId` 带到新用户下触发 403。
- 刷新页面不要求恢复 UI 线程（上下文在服务端，但新页面会生成新 threadId）——此为本期已知限制，写入 §7。

### FR5 多轮追问评测

- 新增 `DIALOGUES` 数据集：不少于 8 组对话，每组 2–3 轮，覆盖：
  - 省略式追问：只换地区 / 只换月份 / 只换产品 / 只换人员；
  - 口径继承：日期范围、筛选条件、同比/环比方式在追问中被正确沿用；
  - 跨轮下钻：上一轮的极值/分组结果成为下一轮的过滤条件。
- 评测流程：同一组内首轮 `fresh: true` 建新线程，其余轮次同 `threadId` 续问；每轮用现有 `scoreAnswer` 打分；一组全轮准确才算通过，单独汇报“多轮对话 x/y”。
- 期望值继续用独立手算口径（与种子数据核对），不引用查询引擎结果。

## 5. 验收标准

1. `npm test`（oracle）仍 20/20。
2. 持久化冒烟：起服务问第 1 轮 → 杀进程 → 重启（同会话目录）→ 同 `threadId` 问追问轮，答案数字正确且 `resumed=true`。
3. 多轮评测：`DIALOGUES` 全部组通过（每轮准确、编造 0 为佳，编造 >0 记录不拦）。
4. 全量回归：单轮 20 + 多步 4 + 安全 2 指标不回退（数字准确率保持 100%）。
5. 跨用户访问他人 `threadId` 返回错误且不泄漏历史。
6. 前端 `npm run ui:build` 通过。

## 6. 风险与对策

- **会话文件膨胀**：本期数据量小不处理；索引里记录 turns，下一迭代做归档/淘汰。
- **上下文越聊越长导致口径漂移**：评测里专门放“长链继承”组（如三轮连续换口径）；漂移先靠评测暴露，不在本期上 compaction。
- **同线程并发**：沿用忙碌保护并细化到线程粒度；全局并发调度列入后续产品化迭代。
- **索引与文件不一致**：索引仅作加速与元数据，恢复时以会话文件存在为准；文件缺失则把该线程视作不存在。

## 7. 已知限制（本期接受）

- 刷新页面后 UI 不回显历史消息（FR3 已备好 history 接口，下一迭代接）。
- 同一用户在两台设备用同一 threadId 同时提问会触发 429，需等当前轮结束。
- 会话目录为本地文件，多实例部署不共享——产品化时换共享存储再议。
